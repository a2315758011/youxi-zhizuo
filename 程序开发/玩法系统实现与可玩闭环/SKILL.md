# 玩法系统实现与可玩闭环

## 目标

把策划中的玩法变成玩家能实际操作、能获得清晰反馈、能完成一局并再次开始的游戏。不得把“场景能打开”“角色能移动”当成玩法完成。

## 一、规则先于场景脚本

实现前把规则整理为最小玩法规格：
- 玩家目标与失败条件；
- 玩家可执行的语义动作；
- 核心循环（行动 → 世界响应 → 资源/状态变化 → 新决策）；
- 关键实体及其状态；
- 资源、冷却、伤害、得分等规则；
- 胜利、失败、暂停、继续和重开；
- 边界条件与不可发生的状态。

规则必须可观察、可判定。简单玩法用表格或状态图即可，不要求大型设计文档。

## 二、最小可玩闭环

所有游戏至少验证与产品类型相符的闭环：

开始/进入
→ 玩家输入
→ 玩法规则处理
→ 世界状态变化
→ 视觉/音频/界面反馈
→ 目标进度变化
→ 胜利或失败
→ 结果展示
→ 重开/继续。

若某款游戏没有传统胜负（如沙盒、创作工具），必须定义其对应的完成、保存、退出和恢复闭环，不强行添加胜负系统。

## 三、按玩法类型实现

### 角色与移动
- 输入映射、移动速度、加速度/阻尼（确有需要时）、边界和碰撞。
- 跳跃、冲刺、攀爬等动作只实现策划明确存在的部分。
- 状态切换必须处理落地、受击、死亡、暂停和重开时的退出清理。

### 战斗与伤害
- 攻击触发条件、有效窗口、目标筛选、命中判定、伤害来源和结算规则明确。
- 区分攻击表现与权威命中逻辑；动画事件只在项目架构允许时通知规则层。
- 处理无敌帧、击退、死亡、掉落和重复命中；没有需求的机制不擅自增加。

### 敌人与 NPC
- 简单行为优先有限状态机；只有行为分支、优先级和中断复杂到难以维护时才考虑行为树；需要连续权衡多个行动时才考虑效用 AI。
- 寻路只在存在真实路径需求时引入，处理不可达目标和动态障碍。
- 敌人行为要有可观察状态与可复现测试，避免每帧重复创建对象或重算昂贵决策。

### 塔防与波次玩法
- 明确刷怪入口、路径、波次、敌人存活数、目标生命、塔位/建造规则、攻击范围、目标选择、伤害与升级成本。
- 每个敌人只在正确的路径和波次状态中参与计数；死亡、到达终点、销毁必须只结算一次。
- 炮塔攻击与敌人移动使用明确的逻辑规则，不能依赖视觉动画判断命中。
- 验证波次结束、下一波触发、玩家失败、全部波次胜利和重开状态清理。

### 关卡与任务
- 入口、出口、关键路径、阻挡、触发区和目标条件明确。
- 验证路线可达、目标可完成、软锁/死锁不存在。
- 关卡内容使用稳定 ID；不能以数组顺序或显示名称作为长期引用。

### 资源与经济
- 定义资源来源、消耗、上限、溢出、负数和失败处理。
- 购买/升级必须先检查条件，再一次性提交资源扣除和状态变更，避免重复输入导致重复扣款。
- UI 显示值从权威玩法状态派生，不维护第二份互相漂移的数据。

## 四、输入与反馈

- 将设备输入转为移动、攻击、确认、取消、拖拽等语义动作。
- 键鼠和触控只在目标平台需要时实现；不要假设鼠标点击等于手机触控。
- 输入必须有清晰即时反馈；长按、连点、重复事件和焦点丢失按玩法需要处理。
- 反馈至少让玩家看懂：动作是否成功、资源是否变化、目标是否受影响、当前处于什么状态。
- 特效和音效增强反馈，但不能成为唯一信息渠道。

## 五、状态和数据一致性

- 玩法规则持有权威状态；UI、动画、音效和粒子是表现层。
- 每次状态变化通过单一规则入口完成，避免多个脚本分别修改同一数值。
- 暂停时停止相关逻辑更新；重开时清除旧波次、计时器、输入缓存、临时实体和旧事件。
- 死亡/销毁/结算必须幂等，避免重复奖励、重复扣血或计数错误。
- 需要保存的字段才进入存档；临时表现状态不写入长期存档。
- 内容更新使用稳定 ID，并考虑旧存档引用。

## 六、实现顺序

1. 复核策划需求与现有工程，不重复开发。
2. 建立最小规则规格和状态表。
3. 用占位素材先实现一个可重复的核心循环。
4. 完成玩家输入、规则变化和明确反馈。
5. 完成胜负/完成条件、结算与重开。
6. 加入必要的动画、音效、UI 和真实素材。
7. 对代表性边界条件编写自动化测试。
8. 在目标平台真实运行，验证输入、显示、性能和生命周期。
9. 通过试玩记录收集理解问题和手感问题，再调整数值。

不要先批量制作内容或搭建编辑器，再验证核心玩法。

## 七、最小测试矩阵

每个玩法至少挑选适用用例：
- 正常操作是否产生预期结果；
- 无效输入是否被正确拒绝；
- 边界数值（0、上限、临界值）；
- 连续/重复输入是否重复结算；
- 暂停后继续是否恢复正确；
- 胜利/失败后是否停止不应继续的逻辑；
- 重开后是否完全回到初始状态；
- 关键资源/存档读写是否保持一致（适用时）。

塔防额外检查：敌人死亡与抵达终点的计数、炮塔目标选择、波次完成、目标生命归零、重开后无残留敌人。

## 八、验收等级

- 规则通过：策划规则无冲突，边界有定义；不代表代码已实现。
- 逻辑通过：关键规则测试通过；不代表场景可玩。
- 场景通过：真实引擎场景可操作并完成一局；不代表目标设备通过。
- 设备通过：目标设备输入、分辨率、生命周期和性能通过。
- 玩家体验通过：真实试玩者理解并完成核心循环，问题有记录。

任何缺失层级必须明确标记，不得用较低层级冒充完整通过。

## 九、交付记录

记录游戏版本、引擎版本、构建 ID、提交、测试种子、平台、设备、操作方式、通过/失败/未运行项、截图/录屏/日志位置、已知问题和回滚点。

## 反过度设计约束

- 不为一个简单玩法建立通用 ECS、复杂事件总线、脚本 DSL 或行为树框架。
- 简单敌人使用少量状态即可，不强行使用 BT/Utility AI。
- 不为单机原型增加服务器、账号、支付、在线遥测或复杂安全系统。
- 不为展示架构而拆分过多脚本；模块边界以真实变化原因和维护收益为准。
- 不为了覆盖率写大量无业务意义的测试；优先验证会导致软锁、错账、无法通关和无法重开的关键规则。
