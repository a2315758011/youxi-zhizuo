# 版本发布与线上维护手册

## 1. 版本身份

每个候选版本必须记录：

| 字段 | 说明 |
|---|---|
| 游戏版本 | 对外可见版本号 |
| 构建编号 | 每次构建唯一标识 |
| 代码提交 | Git commit SHA |
| 资源版本 | 资产清单或资源包版本 |
| 引擎/SDK | 精确版本 |
| 目标平台 | Windows/Web/Android/微信/抖音等 |
| 构建时间 | 使用统一时区 |
| 测试报告 | 对应本次构建的证据位置 |
| 回滚版本 | 上一稳定构建及获取位置 |

## 2. 发布通道

- 开发版：允许调试信息，不面向普通玩家。
- 内测版：验证新功能、兼容性和内容质量。
- 候选版：功能冻结，仅修复发布阻断问题。
- 正式版：通过发布门禁后发布。
- 热修复版：针对生产问题的最小修复，必须补齐回归测试。

不同项目可以简化通道，但必须区分测试版本和正式版本。

## 3. 发布门禁

发布前逐项检查：

- [ ] 目标平台生产构建成功。
- [ ] 核心流程冒烟测试通过。
- [ ] 影响范围内回归测试通过。
- [ ] 首次安装和旧版本升级通过。
- [ ] 旧存档加载/迁移通过（适用时）。
- [ ] 资源清单无缺失、错误引用和意外开发文件。
- [ ] 目标设备性能达到预算。
- [ ] 日志、崩溃诊断和隐私开关符合要求。
- [ ] 许可、平台政策、隐私和商店资料已核对。
- [ ] 上一稳定版本可恢复，数据回滚策略明确。
- [ ] 发布说明、已知问题和支持方式已准备。

任何关键项未测试，状态必须为“未验证”；不得用警告替代硬性发布条件。

## 4. 生产监控

仅采集排障和产品判断必需的最小数据：

- 崩溃/未处理异常数量与版本分布；
- 启动失败、加载失败、卡死和关键流程失败；
- 帧时间、内存峰值、资源加载耗时的聚合值；
- 关卡/模式级匿名聚合指标（确有必要时）；
- 服务端错误、延迟、请求失败率（联网游戏适用）。

禁止默认采集玩家聊天、完整存档、账号凭据、敏感 URL 参数或无关设备信息。遥测应可关闭，禁用后不能影响核心玩法。

## 5. 故障分级与响应

| 级别 | 典型情况 | 处理原则 |
|---|---|---|
| S0 紧急 | 数据丢失、支付/安全事故、大面积无法启动 | 立即止损、暂停发布/服务，保全证据 |
| S1 严重 | 核心玩法无法继续、大量崩溃 | 优先回滚或发布最小热修复 |
| S2 一般 | 部分设备/关卡/功能异常 | 定位影响范围，安排修复版本 |
| S3 轻微 | 表现瑕疵、非关键体验问题 | 纳入迭代，明确优先级 |

响应流程：确认影响 → 保全日志和构建 → 止损 → 复现 → 根因分析 → 修复/回滚 → 回归 → 发布说明 → 复盘。

## 6. 存档与数据保护

- 存档必须包含 schema 版本。
- 写入使用临时文件、校验、备份和安全替换策略。
- 迁移按版本逐步执行，迁移前保留原始数据副本。
- 新版本必须测试至少一个旧版本存档样本。
- 无法识别的更高版本存档不得强行覆盖。
- 云存档需要定义冲突处理、设备切换、离线修改和服务端权威规则。
- 代码回滚与数据回滚分开评估，禁止假设二者自动一致。

## 7. 回滚演练

每个正式项目至少保留一个可启动的上一稳定构建。发布前检查：

1. 能定位上一稳定构建。
2. 能在隔离环境安装并启动。
3. 能恢复兼容的数据副本。
4. 确认回滚后不会破坏新版本已经写入的数据。
5. 明确回滚负责人、触发条件和用户告知内容。

## 8. 更新节奏与玩家反馈

- 每个版本明确更新目的、玩家可见变化和已知问题。
- 小修复优先合并，避免无价值频繁发布。
- 大功能先灰度/内测，再扩大范围（平台支持时）。
- 活动、限时奖励、经济参数和远程配置必须有有效期、默认值、回滚值和审计记录。
- 玩家反馈转成可复现问题，不以单条意见直接改核心规则。
- 不在没有数据依据时承诺固定更新频率或虚构玩家指标。

## 9. 月度维护检查

- 依赖、引擎、SDK 和平台政策变更；
- 崩溃与启动失败趋势；
- 主要设备性能与包体趋势；
- 存档迁移和备份恢复抽测；
- 资产许可和第三方 SDK 清单；
- 技术债、已知问题和下月维护计划。


## 存档兼容专项门禁

适用时，发布候选版本必须执行 [存档版本迁移与恢复验收规范](./存档版本迁移与恢复验收规范.md)，并提交 [存档兼容回归矩阵](../../项目模板/存档兼容回归矩阵.md)。仅迁移函数单测通过不等于真实旧存档兼容通过；必须使用真实发布样本的副本验证。
