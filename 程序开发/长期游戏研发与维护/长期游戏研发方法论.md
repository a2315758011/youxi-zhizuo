# 长期游戏研发与维护方法论

> 适用范围：长期迭代的 2D/3D、桌面、移动端、网页及小游戏项目。本文是跨引擎治理方法，不替代具体引擎官方文档。

## 1. 核心原则

1. **项目事实优先**：源码、配置、构建产物、运行日志、测试结果和版本提交是事实源；聊天记录不是工程状态。
2. **先恢复再修改**：每次继续项目，先核对项目身份、分支、提交、工作区、运行版本、未完成任务和资源锁。
3. **小步可回退**：每个变更尽量单一目的、范围可控、可独立验证；禁止把多个不相关的大改动混在一个提交。
4. **兼容性作为功能**：存档、资源 ID、网络协议、配置、关卡数据和用户设置都需要版本治理。
5. **数据驱动内容**：频繁变化的数值、敌人配置、掉落、波次、关卡参数尽量从代码分离，带 schema/version 与校验。
6. **可观测但尊重隐私**：日志和崩溃信息只收集诊断所需的最小数据；遥测可关闭，不能成为玩法依赖。
7. **测量后优化**：先复现、采样、定位瓶颈，再修改并在相同场景/设备复测。
8. **可构建、可恢复、可交接**：新环境按文档能构建；已发布版本能回滚；其他执行者能从检查点继续。
9. **不以文档代替运行**：静态检查、编辑器预览、网页能打开均不能替代目标平台真实测试。
10. **免费优先**：优先免费、开源或已有授权工具；采用前核对当前许可、商业使用条件与平台政策。

## 2. 项目长期基线（必须建立）

每个游戏项目至少维护以下资料：

- `docs/GAME_BRIEF.md`：玩家体验、目标受众、平台、核心循环、范围与非目标。
- `docs/TECHNICAL_BASELINE.md`：引擎/编辑器/SDK/依赖版本、目标设备、构建方式。
- `docs/ARCHITECTURE.md`：模块边界、数据流、关键接口、资源生命周期。
- `docs/DECISIONS/`：重要技术决策记录（ADR），写明背景、选项、理由、代价和复审条件。
- `docs/CONTENT_PIPELINE.md`：资产来源、命名、导入、压缩、审核、打包和回滚。
- `docs/SAVE_SCHEMA.md`：存档字段、版本、迁移链、备份与恢复。
- `docs/QUALITY_BUDGETS.md`：帧时间、内存、包体、加载、资源尺寸和设备基线。
- `docs/RELEASES/`：版本说明、构建 ID、提交、测试证据、已知问题和回滚版本。
- `docs/OPERATIONS.md`：故障分级、日志位置、排障步骤、恢复联系人/责任人。
- `CHANGELOG.md`：面向人的版本变化记录。

不是所有小项目都要一次创建全部文件；但长期项目进入正式生产前必须补齐适用项，并明确不适用原因。

## 3. 架构治理

### 模块边界

按职责拆分玩法规则、表现层、输入、关卡/内容数据、存档、音频、网络、平台适配和遥测。避免一个全局管理器承载所有业务。

### 依赖方向

- 核心玩法规则尽量不依赖具体 UI、场景节点或平台 SDK。
- 表现层订阅玩法事件并展示状态，不成为规则唯一来源。
- 平台能力通过适配层接入，避免平台 SDK 渗入全部模块。
- 跨模块通信使用明确接口、事件或消息契约，避免循环依赖。

### 数据与配置

- 静态内容数据与运行时状态分离。
- 配置字段必须有默认值、范围校验和版本信息。
- 关键 ID 永久稳定，不因显示名称或文件路径变化而改变。
- 删除/重命名内容 ID 前，先设计旧 ID 映射与存档迁移。

### 技术债

每项技术债记录影响、复现方式、风险、偿还成本、临时规避和计划版本。高风险债务不得长期隐藏在普通待办中。

## 4. 长期迭代闭环

每次迭代遵循：

1. 从玩家问题、崩溃、数据证据或明确产品目标提出变更。
2. 写清用户价值、范围、非目标、影响模块、兼容风险和验收条件。
3. 检查是否已有功能/资产/工具可复用。
4. 在隔离分支或副本实施，必要时先做技术探针。
5. 更新规则、配置、资产、接口和迁移说明。
6. 执行单元、集成、冒烟、回归、设备和性能测试（按变更影响选择）。
7. 生成候选构建并进行真实体验验收。
8. 更新版本记录、已知问题、测试证据和恢复点。
9. 发布后观察错误率、崩溃、性能和玩家反馈。
10. 发现回归时优先止损/回滚，再修复，不在生产环境盲目热改。

每个需求至少有：编号、价值、负责人、状态、依赖、验收标准、证据、回滚方案。

## 5. 质量保障分层

- 单元测试：纯规则、数值、状态转换、数据校验。
- 集成测试：模块协作、资源加载、存档读写、平台适配。
- 冒烟测试：启动、进入游戏、核心操作、结算、重开。
- 回归测试：已发布核心流程及历史缺陷。
- 设备测试：目标系统、分辨率、输入方式、生命周期。
- 性能测试：代表性最坏场景、长时间运行、资源峰值。
- 内容 QA：资源缺失、引用错误、重复 ID、错误尺寸、动画帧和关卡可达性。
- 发布测试：干净环境安装、首次启动、老用户升级、旧存档加载、卸载/重装策略。

测试用例应标明自动化程度、适用平台、执行版本和证据路径。

## 6. 性能长期治理

1. 为目标平台定义帧时间、内存、包体、加载时长、Draw Call、纹理和音频预算。
2. 选取固定基准场景与固定测试设备。
3. 在发布构建中采样，不以编辑器性能代替真实设备。
4. 先判断 CPU、GPU、内存、IO、网络或资源加载瓶颈。
5. 每次只处理主要瓶颈，并进行前后对比。
6. 对实体数量、粒子、寻路、UI 重绘、资源加载和对象分配设上限。
7. 每次大版本更新复测基准场景，防止性能逐版退化。

## 7. 长期内容生产

- 建立资产唯一 ID、来源、许可、版本、尺寸、格式、依赖、用途和状态清单。
- 角色/敌人/道具/场景/动画采用统一风格规范和命名规则。
- 原始源文件、可编辑文件、运行时压缩文件分层保存。
- 资源导入、压缩、图集和平台转换尽量自动化。
- 资源变更必须检查引用、缺失、重复、包体和运行画面。
- 不允许直接覆盖唯一原始资产；替换需保留历史版本或可恢复来源。
- 第三方素材必须记录来源、许可、商用范围和署名要求。

## 8. 版本与分支治理

- 采用语义化版本或项目明确的等价版本规则：主版本.次版本.修订版本。
- 破坏兼容的变更提升主版本；向后兼容的新能力提升次版本；兼容性修复提升修订版本。
- 每个发布版本绑定代码提交、资源版本、引擎版本、构建 ID 和测试证据。
- 主分支保持可构建；大功能在短期分支完成并及时集成。
- 不把未验证的半成品直接发布到正式渠道。
- 发布前标记候选版本；发布后保留上一稳定版本与回滚说明。

## 9. 风险与安全

- 不在仓库提交密钥、令牌、玩家隐私和生产凭据。
- 在线游戏关键经济、排名、购买和奖励逻辑必须评估服务端权威性与重放/作弊风险。
- 外部输入、存档、网络消息和配置均需校验。
- SDK、插件和第三方依赖记录版本、许可、维护状态与升级风险。
- 平台政策、隐私政策、年龄分级和支付规则按目标地区/平台核验。

## 10. 长期维护节奏

### 每次提交
构建/测试、差异审查、变更记录、风险说明。

### 每次迭代
回归核心流程、更新状态、处理技术债、检查内容与性能影响。

### 每次发布
干净环境构建、升级路径、旧存档、性能、崩溃、回滚验证。

### 每月或每个里程碑
依赖与安全更新评估、崩溃趋势、性能趋势、技术债、备份恢复抽测、内容许可复核。

### 重大版本
架构复审、数据迁移演练、全平台兼容、长时间运行、容量与运营预案。

## 11. 失败恢复与回滚

故障记录必须包含：首次发生版本、影响范围、严重级别、复现步骤、日志/截图、最后正常版本、根因（已知/未知）、临时止损、修复提交、回归证据。

回滚前确认数据是否已发生不可逆变化。代码回滚不能自动撤销玩家数据；涉及存档/经济/云数据时必须单独设计补偿或前向修复。

## 12. 完成标准

长期项目只有在以下条件满足时才可标记为稳定维护：

- 当前主分支可复现构建；
- 核心玩法和历史关键缺陷有回归测试；
- 存档有版本和迁移策略（适用时）；
- 发布有构建标识、测试证据和回滚点；
- 运行错误与性能问题有诊断路径；
- 关键资产有来源、许可和清单；
- 有已知问题列表和下一迭代入口。

“游戏曾经能运行”不等于“当前版本稳定”；“发布过一次”不等于“具备长期维护能力”。
