# 游戏程序开发与代码最小化

## 目标

把用户可观察的游戏需求转成最少、最清晰、可测试、可维护的实现。代码行数不是质量指标；正确性、可读性、运行成本和修改成本才是。

## 开始前：先看工程，不先写代码

按顺序确认：
1. 当前工程目录、引擎与精确版本、目标平台、启动/构建/测试命令。
2. 当前分支、未提交改动、相关资源锁和最近失败记录。
3. 功能入口、调用方、数据结构、场景/Prefab/节点引用和相邻测试。
4. 引擎原生能力、项目已有组件/工具函数，以及仓库可复用实现。
5. 预期行为、非目标、异常路径和可观察验收条件。

只读取与任务有关的文件。简单任务不制作大型架构图；跨模块任务才画最小调用链。

## 最小实现决策

每次变更先回答：
- 最简单能满足需求的实现是什么？
- 当前已有哪个组件或引擎 API 可以直接完成？
- 新增文件、类、依赖、状态或配置是否不可避免？
- 如果不新增抽象，是否仍然清晰可测试？
- 复杂度带来的实际收益能否被测试或运行证据证明？

遵守 KISS、YAGNI、单一职责和最小充分抽象：
- 先写直接实现；出现至少两个真实重复用例且维护收益明确时再提取公共逻辑。
- 不为一个调用点预建工厂、注册中心、服务定位器、插件系统、事件总线或通用框架。
- 不把每个函数包装成独立类，也不把所有逻辑塞进一个巨型 Manager。
- 优先使用引擎节点、组件、信号、资源、动画、输入、计时器和存档能力。
- 不引入第二套游戏时钟、对象生命周期或状态管理机制。
- 不因“以后可能联网/多人/扩展”提前建设服务器、账号、权限、加密和微服务。
- 不为消除几行重复而制造难懂的泛型、继承层级或配置系统。

## 代码实现约束

- 输入层只把键鼠/触控/手柄转换为语义动作。
- 玩法规则负责权威状态和确定性状态转换。
- 场景层负责引擎对象生命周期、呈现和装配。
- 数据层负责配置、稳定 ID 和存档。
- 平台适配只在真实平台需求出现时存在。
- 一个规则只能有一个权威实现位置；UI、动画和特效不得反向决定胜负或伤害等核心规则。
- 避免隐式全局状态、循环依赖、无界队列、无意义缓存和每帧分配。
- 不要为了“安全”增加没有威胁模型支持的防护；先说明资产、攻击入口、影响和最低成本缓解措施。
- 不随意升级引擎、SDK 或依赖；每次升级都要有明确原因、兼容检查和回滚方式。

## 调试与修改

1. 记录预期与实际行为。
2. 收集错误、堆栈、日志、构建版本和最小复现。
3. 沿真实调用链定位根因，不凭猜测叠补丁。
4. 对确定性逻辑先写能在旧实现失败的回归测试。
5. 只修改根因相关的最小范围。
6. 执行失败用例、相邻回归和必要的真实运行验证。
7. 删除临时日志、死代码和无效绕过。
8. 保留修改前恢复点与修改后证据。

如果问题不能复现，先补证据，不得随机改动。

## 代码审查清单

- 是否满足用户明确需求，是否擅自改变玩法？
- 是否重复实现已有功能？
- 是否新增了没有真实使用场景的抽象？
- 是否增加不必要依赖、配置、状态或网络服务？
- 是否存在重复事件、空引用、越界、生命周期错误和资源泄漏？
- 暂停、重开、切场景、死亡和重复输入是否正确？
- 代码与场景、Prefab、资源、存档和配置是否一致？
- 是否有能证明关键行为的测试，而不是只测试实现细节？
- 是否能由另一位维护者快速定位和修改？

审查意见必须给出文件位置、触发条件、实际影响、严重程度和验证方式。没有证据的推测不能包装成确定缺陷。

## 复杂度预算

小改动只需在任务记录中写几句话；跨模块改动才使用正式记录。

| 项目 | 记录内容 |
|---|---|
| 需求与非目标 | 本次要做什么、不做什么 |
| 最小方案 | 最少需要哪些代码和资源 |
| 复用检查 | 已有实现与引擎能力 |
| 新增复杂度 | 文件、模块、依赖、状态、配置 |
| 必要性 | 每项新增解决的真实问题 |
| 验证 | 测试、运行、平台和回归证据 |
| 回滚 | 恢复点和受影响数据 |

不能证明必要性的新增设计应删除。

## 输出要求

每次完成代码任务必须报告：
- 修改的文件与行为；
- 新增代码/依赖/模块及其必要性；
- 实际执行的测试与原始结果；
- 未运行、未覆盖和阻塞项；
- 回滚位置。

静态检查通过不等于功能通过；代码写完不等于游戏可玩。

## 技能边界

本技能约束实现方式和复杂度，不负责完整玩法设计、数值平衡、玩家体验或引擎专属 API。玩法闭环按需使用“玩法系统实现与可玩闭环”；引擎 API 以项目精确版本官方文档为准。
