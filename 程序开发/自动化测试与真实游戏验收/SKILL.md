# 自动化测试与真实游戏验收

## 目标与职责

让每次游戏改动都有可复现的测试证据，同时避免为了测试引入复杂的生产架构。

本技能负责选择和编排测试方式；不重新实现已有技能：
- game-qa：定义测试类型及证据卡；
- gameplay-harness：定义语义输入、回放、项目逻辑时钟和状态 oracle；
- gameplay-validation：定义一次测试究竟能证明什么；
- 本技能：按引擎选择测试执行器、划定最小覆盖范围、组织测试顺序和发布门禁。

## 第一步：读取项目事实

先检查引擎、精确版本、语言和平台；当前测试框架、测试脚本、CI 配置和运行命令；构建 ID、提交和工作区改动；项目已有输入系统、逻辑时钟、存档结构；现有测试是否能在干净环境重现。

已有框架可用时不换框架。一个项目默认只使用一个主要测试执行器，不要为了多一种测试写法同时安装两个测试运行器。

## 第二步：按引擎选择最小工具

### Godot 4

按项目精确版本选择，禁止直接安装最新版而不核对兼容矩阵。

| 项目条件 | 优先选择 | 理由 |
|---|---|---|
| GDScript 项目，纯逻辑/基础单元测试 | GUT | GDScript 原生测试，CLI、JUnit XML |
| GDScript 或 C#，需要场景交互、触控模拟、信号等待 | GdUnit4 | 有 Scene Runner 和场景集成能力 |
| C# 项目，需要贴近节点的输入/交互驱动 | GodotTestDriver（可选） | 它是交互驱动库，不是测试执行器 |
| 无测试插件、只需小型纯 GDScript 探针 | Godot 原生 headless SceneTree runner | 不为少量逻辑测试引入插件 |

已核对的版本参考：
- GUT：9.4 对应 Godot 4.3–4.4；9.5 对应 4.5；9.6.1 对应 4.6；9.7.1 对应 4.7.x。以 GUT 当前 README 兼容表为准。
- GdUnit4：6.2.2 为已发布版本；6.2.x 支持 Godot 4.5、4.6、4.7 系列。4.3/4.4 项目应选择兼容旧版，不可直接套用 6.2.x。
- GodotTestDriver 主要用于 C# 集成测试驱动，不可误认为完整测试运行器。

每个项目只选满足当前测试需求的一个主运行器。需要 Scene Runner、C# 或触控输入时才增加对应能力。

### Unity

优先使用 Unity 官方 Unity Test Framework：
- Edit Mode：纯逻辑、编辑器工具、数据结构；
- Play Mode：运行时状态、跨帧协程、场景交互；
- 需要时在独立 Player 构建中执行 Play Mode 测试；
- 不要把 Edit Mode 通过写成运行时已通过。

### Web / Phaser / Pixi / 其他引擎

优先沿用项目现有测试栈和浏览器自动化。测试逻辑规则与真实浏览器交互分层；不能只依赖 DOM 单测证明游戏画面、帧循环和触控行为正确。

## 第三步：测试分层（只覆盖当前风险）

1. 逻辑单元：数值、规则、状态转换、资源计算、输入映射；
2. 场景集成：场景加载、节点连接、信号、UI、碰撞和资源引用；
3. 确定性回放：固定输入带、随机种子、存档和稳定状态 oracle；
4. 真实运行冒烟：目标构建启动、进入游戏、核心操作、胜负、重开；
5. 真实输入/设备：键鼠、手柄、触控、横竖屏、暂停恢复；
6. 长时间稳定：仅在项目有持续运行、刷怪、放置或在线循环风险时执行；
7. 真人试玩：检验理解、乐趣、难度和自然行为，不能由前六项替代。

小项目不需要机械地实现全部层。每次改动只运行与影响范围匹配的最小集合，并保留关键核心回归。

## 第四步：确定性回放规则

复用项目已有逻辑时钟，不另造第二套固定帧循环。
- 使用语义动作（移动、跳跃、攻击、确认），而不是把物理键码写死在测试用例中；
- 固定随机种子、难度、初始存档、设备和构建；
- 记录每个逻辑步的输入、关键状态字段和有序事件；
- 比较稳定的逻辑状态，不比较随机粒子、相机抖动、对象内存地址和非确定时间戳；
- 第一次出现差异时报告逻辑帧、字段、期望值和实际值；
- 更新基准文件必须写明原因，不自动接受新结果；
- 开启调试作弊、传送、无敌或强制解锁时，证据必须标记为 scripted，不得写成自然通关。

长时间稳定性测试只使用合法输入；使用作弊或强制状态后不得把结果计为自然稳定性证据。

## 第五步：Godot headless 特别约束

- 干净检出后先执行一次资源导入，再运行测试；不要把首次导入耗时混入测试耗时。
- CI 必须读取进程退出码，不只看 stdout 中的 PASS/FAIL 字样。
- 自定义 SceneTree runner 必须显式统计失败并 quit(1)；不能假设 assert() 或 push_error() 自动返回非零。
- 每个异步等待都必须有超时回退，CI 作业也要设置总超时。
- 需要帧、Timer 或信号的测试必须等待场景树进入有效生命周期后再执行。
- 不以 --quit-after 代替业务完成条件；应由测试本身在 PASS/FAIL 时退出。
- 不要仅凭 shutdown 日志文本判断失败；结合测试框架结果、退出码和独立资源泄漏检查。
- headless 测试不证明渲染、真实窗口、输入设备或 GPU 路径正常。

## 第六步：测试报告与证据

每个测试结果必须绑定：
- 测试编号、测试类型；
- 游戏版本、构建 ID、代码提交、资源版本；
- 引擎与测试框架精确版本；
- 平台、设备、输入方式、难度、种子、存档 ID；
- 是否启用作弊/调试覆盖；
- 结果：通过 / 失败 / 阻塞 / 未运行 / 不适用；
- 失败复现步骤、首个差异和原始日志；
- 截图/录屏/报告位置；
- 本轮未覆盖范围。

不允许：
- 静态检查通过 = 游戏可玩；
- headless 通过 = 真实设备通过；
- 自动代理完成 = 真人玩家理解；
- 测试截图 = 游戏完整流程；
- 测试数量多 = 质量高。

## 第七步：最小发布门禁

正式发布至少需要（按项目适用性）：生产构建成功；核心流程冒烟通过；影响范围内回归通过；旧存档迁移与备份恢复通过；目标输入和设备通过；关键性能预算通过；已知问题和未验证项列明；上一稳定版本可回退。

任何关键项未执行都标记未验证，不允许把“未运行”改成“通过”。

~~~

## 反过度设计约束

- 不为小型单机游戏引入遥测服务、测试服务器、复杂权限系统或第二套游戏时钟。
- 不为自动化测试而把作弊接口暴露到正式玩家版本。
- 不需要的引擎插件不安装；仅在真实项目中按兼容版本安装。
- 不以测试框架的功能数量决定采用；先用最小探针证明它能覆盖本项目。
- 不用 CI 替代本地实际运行，也不让 CI 取代真人试玩。
