# AI 游戏代码工程总规范

## 0. 定位

本规范约束 AI 如何在真实游戏工程中编写和修改代码。目标不是生成更多代码，而是交付正确、可维护、符合项目现状、可验证、可恢复的游戏功能。

它是工程入口与路由，不替代各领域专业技能。执行时按任务加载最多 3 个专业工程技能 + 1 个必要引擎技能；简单任务可更少。

## 1. 绝对优先级

1. 用户明确需求、验收条件与已锁定决策；
2. 当前项目实际运行行为、现有架构、数据契约和资源锁；
3. 项目 AGENTS.md、ADR、代码约定、测试基线；
4. 对应引擎和语言的官方文档、精确版本 API；
5. 本仓库通用工程技能与第三方参考；
6. AI 自己的推断。

任何推断不得覆盖真实证据。发现需求与当前实现冲突时，先报告冲突和影响，不擅自选择业务行为。

## 2. 开始改代码前必须做的工程侦察

先读取：
- 仓库 AGENTS.md、README、相关模块说明、架构决策；
- 目标功能实际代码、调用方、数据结构、资源引用和相邻测试；
- 引擎/编辑器/语言/SDK 精确版本与依赖锁文件；
- 当前分支、提交、工作区未提交改动、其他执行者和资源锁；
- 可运行命令、构建配置、测试基线、最近失败日志；
- 历史版本中已存在的行为、兼容契约和已知问题。

必须画出与任务有关的最小数据流/调用链：输入 → 状态/规则 → 副作用 → UI/动画/音频/存档/网络 → 输出。不要只读用户指出的一个文件就修改。

## 3. 需求到实现的闭环

新功能、玩法创新、需求不清或存在多种方案时，按需读取 Superpowers 的需求澄清与方案构思技能；简单明确的小修复不强制完整构思流程。跨模块、多阶段任务读取实施计划编写与跨会话实施跟踪。用户已经锁定的目标和决定不得被重复讨论推翻。

1. 将需求拆成可观察的行为和验收标准；
2. 标出不在范围内的行为、边界条件和失败状态；
3. 对照现有实现，区分已完成、部分完成、缺失、错误、未知；
4. 识别受影响的模块、数据、场景、资源、平台和旧存档；
5. 设计最小实现与回归测试；
6. 实现后逐条回到验收标准，给出代码位置与测试证据；
7. 任何未运行、未覆盖或环境不可用的项目标记 UNVERIFIED/BLOCKED，不得写成通过。

大型功能或跨会话任务，使用需求差距分析与计划跟踪技能；小改动不强行写大型设计文档。

## 4. 架构与代码设计原则

### 4.1 简单优先，不等于草率

- KISS、YAGNI、最小充分抽象；只为已经出现的复杂度建立抽象。
- 先寻找已有服务、节点、组件、资源、工具函数和引擎原生能力。
- 不因“未来可能扩展”创建框架、注册中心、事件总线、服务定位器、微服务、插件系统或第二套时钟。
- 不为消除少量重复而制造难懂的泛型、继承层级或配置系统。
- 一个函数/模块要有明确责任；当两个以上流程重复同一机制且确有统一维护收益时，再提取共享服务。
- 复杂度新增必须说明：解决哪个真实问题、为什么现有实现不够、带来哪些运行与维护成本。

### 4.2 依赖方向与模块职责

- 输入适配层负责接收设备输入并转为语义动作；
- 玩法规则层负责确定性规则和状态转换；
- 场景/节点层负责引擎生命周期、呈现与对象装配；
- 数据层负责资源定义、存档和内容版本；
- 平台/外部适配层负责系统 API、网络、文件、广告或商店接口（项目确实需要时）。
- 依赖方向要清楚；核心规则尽量不直接依赖 UI、音频、文件系统和具体设备。
- 不把整个游戏做成一个巨型 Manager；也不把每个小行为拆成独立类。
- 跨模块通信优先采用项目已存在的机制，避免隐式全局状态和循环依赖。

### 4.3 游戏状态与时间

- 明确区分权威游戏状态、表现状态、临时 UI 状态和可重建缓存。
- 对状态转换定义合法前置条件、结果和失败分支。
- 物理更新、渲染更新、逻辑回合和网络时间不可混为一谈。
- 使用引擎/项目既有时钟与生命周期，不擅自引入第二套 tick。
- 需要确定性回放时固定输入、随机种子和逻辑步，并只比较稳定状态字段。
- 暂停、切场景、死亡、重开、断线、恢复和重复输入必须纳入相关状态机检查。

### 4.4 数据与内容

- 配置/静态内容优先数据驱动，行为复杂度高时才引入脚本策略。
- 关卡、道具、敌人、任务和角色使用稳定 ID；已发布 ID 不复用。
- 存档保存权威数据，不保存对象引用、临时 UI 或可重建缓存。
- 结构变更必须考虑 schema 迁移、备份、失败恢复和旧版本读取。
- 数组下标、显示名称和资源路径不能作为跨版本稳定身份。

### 4.5 代码可读性

- 遵循当前项目已有语言约定和格式工具，不强行套用其他语言的命名方式。
- 名称表达意图；避免 x、tmp、data、manager 等缺乏语境的泛名。
- 优先显式类型、明确边界和小型纯函数；避免无必要的 any/动态类型。
- 减少可变共享状态；函数不要暗中修改调用方数据。
- 注释解释原因、约束和不明显的引擎陷阱，不复述代码。
- 不保留调试输出、临时绕过、死代码、无效 TODO、复制粘贴的伪抽象。
- 复杂算法和重要数据契约要写明输入、输出、不变量和失败条件。

## 5. 游戏代码实现专项要求

按项目适用性检查：
- 输入：语义动作、设备映射、按键重绑、缓冲、重复输入、焦点与触屏；
- 角色控制：状态机、地面/空中、碰撞、坡面、边界、受击/无敌帧；
- 物理：固定时间步、碰撞层、穿透、CCD、确定性要求；
- AI：简单行为优先有限状态机；复杂选择才考虑行为树/效用 AI；寻路要处理不可达与动态障碍；
- 战斗：攻击窗口、命中判定、伤害来源、目标筛选、击退、死亡和掉落；
- UI：锚点、安全区、分辨率缩放、焦点导航、弹窗栈、暂停状态；
- 动画：逻辑状态与动画状态一致，不能靠动画片段名称决定权威玩法；
- 场景：加载/卸载、节点生命周期、资源引用、信号连接与重复实例；
- 多人游戏：只有真实联网需求时才设计权威端、同步、预测、重连与作弊面；
- 构建：目标平台导出、资源导入、代码裁剪、原生插件与包体限制。

不要将所有项目强行套用上述所有子系统。只检查当前游戏确实具有的能力。

## 6. 缺陷修复流程：先证据，后改动

没有可复现或可验证的证据，不做随机补丁。优先结合 Superpowers 系统化调试原文与本仓库系统化缺陷修复技能；二者合并为一个诊断流程，不重复跑两套检查。
1. 明确预期行为和实际行为；
2. 获取错误、堆栈、日志、构建和运行版本；
3. 构造最小稳定复现或失败测试；
4. 沿调用链追踪状态、输入、资源、时序和副作用；
5. 提出可证伪的根因假设；
6. 用最小实验排除错误假设；
7. 修复根因，不只隐藏报错或增加无条件重试；
8. 运行失败测试确认它先失败、修复后通过；
9. 运行相邻功能和历史行为回归；
10. 保留证据、根因和回滚点。

反复失败且无法用单个测试重现时，切换到系统根因分析；性能问题先测量 CPU/GPU/内存/帧时间，不以猜测优化。

## 7. 测试设计原则

对可确定的功能逻辑和 Bug 修复，默认采用测试驱动开发（TDD）：先写针对需求/缺陷的测试，观察旧实现失败，再写最小实现使测试通过，最后重构并复测。若测试无法可靠观察（纯视觉、美术资产、物理手感或平台设备行为），先固定基线、定义可观察验收标准，再进行真实运行验证；不得为了形式制造无意义测试。

- 测试要验证行为与不变量，而不是复制实现细节。
- 每个关键缺陷应有能在旧代码上失败的回归测试。
- 对规则和边界使用表驱动、属性测试或固定种子随机测试（适用时）。
- 区分单元、场景集成、端到端、真实设备、长时间稳定和真人试玩。
- 覆盖成功路径、失败路径、边界、重复输入、暂停/恢复、重启、数据损坏和兼容路径（按影响范围）。
- 测试必须有明确超时、失败退出码、可读报告和可复现环境。
- 不以覆盖率数字替代测试质量；关键断言必须证明能捕获错误。
- 测试未运行标记 SKIP/UNVERIFIED，并解释原因。

## 8. 代码审查与历史回归

审查意见必须先验证技术事实和项目上下文，不因审查者身份而盲从；同样不因意见不符合预期而直接拒绝。重大变更在完成前请求真正独立的审查者；若当前环境没有独立审查工具，则标记未执行独立审查。完成前必须读取实际测试输出，遵循“证据先于完成声明”。

审查时优先检查：
1. 是否真正满足需求；
2. 是否改变了原有功能、默认值、顺序、时序或错误行为；
3. 状态机是否遗漏枚举、转移或退出清理；
4. 是否有空引用、越界、竞态、重复事件和资源泄漏；
5. 是否有安全边界、权限、用户输入和存档完整性问题；
6. 是否有无证据的复杂抽象、重复实现和调试残留；
7. 是否有性能热点和无界内存/队列；
8. 文档、配置、测试、资源清单和代码是否同步。
每个发现给出文件/行、触发条件、实际影响、严重级别、最小修复建议和验证方法。没有可复现影响的猜测不得包装成确定缺陷。

高风险、跨模块或复杂重构可启用独立复核；只有真正独立的审查者/模型才算多模型复核。

## 9. 安全、性能与依赖治理

### 安全
- 先判断游戏威胁面：离线单机、联网联机、账号、交易、排行榜、云存档、用户生成内容等。
- 离线单机不套用企业级权限系统；联网功能必须检查信任边界、服务端权威和输入验证。
- 不提交密钥、令牌、用户数据；日志与截图脱敏。
- 第三方插件、原生库、资源包和构建脚本检查来源、许可证、版本和供应链风险。

### 性能
- 先测量帧时间、CPU、GPU、内存、GC、Draw Calls、资源加载和包体，再决定优化。
- 目标平台与目标硬件决定预算；不能用开发机单一结果代表手机。
- 优先修复真实热点、重复分配、过量实例、昂贵查询和不必要资源常驻。
- 对象池、缓存、异步加载和多线程只在测量证明有收益时使用。
- 优化前后使用同场景、同设备、同构建配置对比。

### 依赖
- 先核实当前锁定版本、引擎兼容、许可证和维护状态。
- 不随意升级全部依赖；按风险分批，一次一个主要升级原因。
- 大版本先读迁移说明，单独提交并保留回滚。
- 不为了一个简单功能引入大型框架。

## 10. 交付与证据

每次代码任务结束输出：
- 修改目标和范围；
- 修改文件及责任；
- 关键设计选择与被拒绝的复杂方案；
- 实际执行的命令/测试及精确版本；
- 通过、失败、阻塞、未运行数量；
- 真实运行环境、构建 ID、提交；
- 旧行为回归与存档兼容结果（适用时）；
- 未验证事项、风险和恢复方式；
- 任务进度百分比及其验收依据。

不得把“代码已写入”“静态检查通过”“单元测试通过”混写成“游戏已完成”。

## 11. 按需技能路由

| 任务 | 优先加载的技能 | 组合边界 |
|---|---|---|
|---|---|---|
| 新模块/新系统设计 | 需求澄清与方案构思（适用时） + 技术方案与架构决策 + 代码工程规范 | 需要时加引擎技能；简单任务省略构思 |
| 可测试功能/缺陷实现 | 测试驱动开发 + 代码变更完整性 | 非确定性视觉/手感任务用基线验收替代纯 TDD |
| 架构审计/模块混乱 | 架构审计 + 代码职责与分层 | 只读审计先于改动 |
| 功能实现完工 | 代码变更完整性 + 高价值测试设计 | 再按影响选引擎技能 |
| Bug/崩溃/测试失败 | 系统化调试 + 系统化缺陷修复 | 合并成一个根因流程；流程性反复故障再加系统根因分析 |
| 重构/清理 AI 代码 | AI代码清理与重构 + 安全重构与死代码核查 | 必须保行为回归 |
| PR/代码差异审查 | 代码审查 + 历史行为回归检查 | 审查意见须技术核验；高风险时加独立复核 |
| 完成/发布声明 | 完成前证据验证 + 全链路回归扫描 | 必须读取当前构建的实际输出 |
| 测试覆盖不足 | 测试缺口审计 + 高价值测试设计 | 不以行覆盖率为唯一指标 |
| 卡顿/掉帧/内存增长 | 性能与可靠性审计 | 必须先采样和测量 |
| 联网、账号、存档、交易 | 安全审计 + 错误处理规范 | 依据实际威胁面 |
| 依赖升级 | 依赖升级治理 | 分批、可回滚 |
| 日志诊断 | 日志与隐私规范 + 错误处理规范 | 先脱敏 |
| 复杂跨会话任务 | 需求到代码差距分析 + 跨会话实施跟踪 | 小任务不强制 |
| 计划太复杂 | 方案反过度设计 | 只删无价值复杂度 |

## 13. 验证等级

- A：在真实游戏项目中经过至少一项实际任务验证，有前后对照、缺陷/效率证据和回归结果；
- B：已导入、来源/许可证核对并完成文档审阅，未在用户项目验证；
- C：候选来源，未完成质量和兼容审查；
- D：重复、过时、不适用或有无法接受的依赖，不启用。
