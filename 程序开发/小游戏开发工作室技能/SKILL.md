# 小游戏开发工作室

## 定位

统一调度游戏制作与长期维护所需专业工作。开始前读取仓库 AGENTS.md、README.md、[从零制作游戏全流程与 AI 简洁性约束](../从零制作游戏全流程与AI简洁性约束.md)、[专业游戏技能库来源与中文调度索引](../专业游戏技能库来源与中文调度索引.md)、长期游戏研发方法论和对应项目文档；检查实际工程、代码、资产、分支、历史提交、运行版本和测试证据。

## 第一原则：复杂度必须有证据

- 简单需求用简单实现；几行代码能可靠解决的，不得扩写成大型框架。
- 不为假想扩展预建插件系统、事件总线、注册中心、工厂、微服务或复杂权限体系。
- 不把单机小游戏设计成企业级安全架构。
- 新增类、文件、依赖、服务、配置和安全控制，必须说明对应的真实需求或风险。
- 优先使用引擎原生能力与项目现有模块。
- 不为追求代码短而删除必要校验；目标是最小、清楚、正确、易测试的实现。
- 修改前检查现状；修复只改最小责任范围，不顺手重写无关模块。

## 技能调度：最少而够用

- 先根据用户目标识别当前制作阶段、游戏类型、引擎和具体任务。
- 每个阶段最多选择 3 个专业学科/类型技能 + 1 个必要引擎技能。
- 只读取本阶段需要的技能正文；参考文件按需打开，不递归加载所有相关技能。
- 简单敌人先用几条条件判断或有限状态机；只有决策复杂度真实需要时才用行为树/效用 AI。
- 只在目标游戏需要时启用联网、账号、云存档、交易、反作弊、遥测和线上运营技能。
- 外部技能的原始文档、脚本和依赖必须先审阅；导入不等于安装，安装不等于验证。
- 第三方技能默认 B 级（已导入、未在用户项目验证）；真实项目测试通过才可升 A 级。
- 详细路由见 [专业游戏技能库来源与中文调度索引](../专业游戏技能库来源与中文调度索引.md)。

## 任务入口与恢复

1. 确认项目名称、编号、根目录、仓库、主分支和当前提交。
2. 检查工作区差异、未提交修改、其他执行者、资源锁和未完成任务。
3. 读取项目引擎/编辑器/SDK精确版本、依赖锁文件和目标平台。
4. 恢复最近检查点、已知问题、技术决策、测试基线和回滚点。
5. 根据本次任务选择最小专业技能组合；不为无关任务加载整套技能。

## 自动调度的专业角色

1. 游戏总导演：需求恢复、范围锁定、依赖图、任务拆分、进度和集成。
2. 游戏策划：核心循环、规则、状态机、数值、难度、经济和测试用例。
3. 游戏程序：架构、输入、碰撞、AI、寻路、存档、网络和构建。
4. 游戏美术总管：风格规范、角色、敌人、场景、道具、UI 与资产验收。
5. 动画特效：动作状态、关键帧、粒子、播放和性能验证。
6. 关卡设计：地图、地形、障碍、路径、刷怪、节奏和可达性。
7. UI/交互：菜单、HUD、背包、商店、触屏和响应式布局。
8. 音频设计：音乐、环境音、UI、攻击、命中和混音。
9. 测试与性能：单元、集成、冒烟、回归、兼容、帧率、内存和崩溃诊断。
10. 发布与维护：版本、构建、存档迁移、线上监控、故障响应、回滚和复盘。

## 标准生产流程

1. 恢复工程、用户确认的玩法、项目决策和运行状态。
2. 锁定玩家体验、核心循环、平台、输入、胜负、范围与风险。
3. 制作玩法简报、规则规格、状态机、数据表和验收用例。
4. 完成目标平台最小技术探针。
5. 制作可玩的原型：输入→核心规则→反馈→胜利/失败→重开。
6. 制作代表性垂直切片，验证美术、UI、动画、音频到运行的完整链路。
7. 先做风格锚点和少量样例，通过验收后分批扩展内容。
8. 集成资源并执行引用、版本、性能和跨模块检查。
9. 在目标设备和平台构建上进行真实测试。
10. 交付源码、资源、可运行版本、测试证据、限制和恢复说明。

## 长期研发流程

长期游戏必须遵循 [长期游戏研发方法论](../长期游戏研发与维护/长期游戏研发方法论.md) 与 [版本发布与线上维护手册](../长期游戏研发与维护/版本发布与线上维护手册.md)。

每次迭代：需求证据 → 影响分析 → 范围与验收锁定 → 小步实现 → 自动测试 → 真实运行 → 回归 → 版本记录 → 发布观察。

长期项目必须维护架构边界、技术决策、依赖版本、资产 ID/许可、存档 schema、性能预算、崩溃诊断、已知问题和回滚点。老玩家存档兼容、稳定 ID 和数据恢复视为核心功能，不是发布后再补的可选项。

## 质量与交付纪律

- 代码存在、页面打开、静态检查通过或单张截图不能代替可玩验收。
- 不允许占位图冒充正式美术，不允许重复帧或整图平移冒充真实动画。
- 角色身份、装备、场景空间、道具位置、锚点和动作连续性必须一致。
- 关键按钮必须实际可用；测试快速重复输入、暂停恢复、重开、异常退出和存档。
- 测试证据绑定当前代码提交、资源版本和构建标识。
- 失败必须记录现象、复现、证据、根因、修复和回归结果。
- 默认简体中文沟通、文件夹和报告；技术标识保留原名并用中文解释。
- 状态使用 VERIFIED、FAILED、BLOCKED、UNVERIFIED、NOT_APPLICABLE；未实际测试不得宣称成功。
- 进度百分比必须由任务权重和验收证据计算，不能凭感觉填写。

## 移动端与资产质量门禁

- 涉及手机或 PC+手机双平台时，按需读取 [移动端 2D 游戏生产与真实设备验收](../移动端2D游戏生产与真实设备验收.md)，不能用桌面浏览器打开代替真机触控验收。
- 涉及角色、植物、敌人、Boss、NPC 等动态单位时，按需读取 [2D 美术资产与运行时交付规范](../2D美术资产与运行时交付规范.md)，必须验证动画状态闭环、锚点、帧序和运行时播放。
- 评估技能效果或决定保留/淘汰时，按需读取 [游戏技能效果评估与对照测试规范](../游戏技能效果评估与对照测试规范.md)，必须有对照组和真实证据。

- [ForgeSkills 质量验证与视觉迭代调度](../ForgeSkills质量验证与视觉迭代调度.md)：玩法系统契约、四层测试、独立验证、视觉量化迭代。


- 涉及首次体验、玩家理解、难度/经济平衡或操作手感时，按需读取 [玩家体验与游戏平衡评估](../玩家体验与游戏平衡评估/SKILL.md)，使用 [玩家试玩记录表](../../项目模板/玩家试玩记录表.md) 记录可复现证据。真人试玩、AI 黑盒试玩和设计推演必须分开报告。


## AI 编写代码的工程门禁

任何新增功能、代码修复、架构调整、重构和发布前审查，先读取 [AI 游戏代码工程总规范](../AI游戏代码工程总规范/SKILL.md)，按需选择通用工程技能。不要把引擎 API 使用技能误当作完整的软件工程能力：代码必须经过需求映射、架构边界检查、根因分析（修 bug 时）、历史回归、真实运行和证据记录。


## 需求澄清、测试驱动与完成前验证

新玩法或多方案功能按需读取 [Superpowers 精选技能](../../外部专业技能库/superpowers/README.md)。可确定的逻辑功能优先测试驱动开发；缺陷先复现再定位根因；完成前必须读取当前构建的测试输出。小型明确改动不做不必要的方案仪式；视觉/物理手感任务用基线和真实运行验收，不强行伪造单元测试。
