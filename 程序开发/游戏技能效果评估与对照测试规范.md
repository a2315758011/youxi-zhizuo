# 游戏专业技能效果评估与对照测试规范

## 目的

不以技能数量、作者宣传、仓库星数或文档篇幅评价技能。验证它是否能在真实游戏任务中带来可重复的质量提升，且没有制造不必要复杂度。

## 评估对象

每个技能必须登记：
- 技能名称、上游仓库、固定提交/版本、原始路径和许可证；
- 适用引擎、精确版本、游戏类型、平台、任务阶段；
- 输入条件、预期产物、禁止越界的责任；
- 依赖的其他技能、脚本、工具和运行环境；
- 评估状态：候选、已导入、静态审阅、工程测试、真实试玩、淘汰。

## 对照实验设计

同一任务、同一工程基线、同一引擎版本、同一设备/模拟器、同一验收用例，比较：

- A 组：不调用该技能，只使用基础工作流。
- B 组：调用该技能，严格遵循其适用部分。
- 必要时 C 组：调用精简后的技能组合，检查是否存在技能叠加收益或冲突。

每组至少重复 3 次，避免一次生成或偶然成功造成误判。涉及随机玩法时固定随机种子；涉及图像生成时记录模型、提示词、参考图哈希和生成参数。不得把不同模型、不同引擎版本或不同资产条件的结果直接比较。

## 固定基准任务

| 编号 | 基准任务 | 主要验证点 |
|---|---|---|
| GAME-BENCH-01 | 2D 最小可玩循环：开始、移动/交互、得分/失败、重开 | 核心规则、输入、状态流、基础可玩性 |
| GAME-BENCH-02 | 塔防波次：敌人路径、单位攻击、伤害反馈、波次胜负 | 玩法规则、AI 复杂度、数值、动画状态闭环 |
| GAME-BENCH-03 | 手机触控：点按、拖动、长按、横竖屏、安全区、暂停恢复 | 触控准确性、响应式布局、真实设备行为 |
| GAME-BENCH-04 | 存档与长期运行：保存、重启恢复、旧版本迁移、资源释放 | 存档完整性、迁移、内存/实例泄漏、恢复可靠性 |

项目类型不匹配时标记 NOT_APPLICABLE，不强行套用。例如卡牌游戏不需要角色跳跃测试。

## 评分维度（每项 0–5 分）

1. 功能正确：验收用例通过率、边界行为、状态一致性。
2. 可玩体验：真实玩家是否能完成目标、反馈是否清楚、操作是否自然。
3. 工程简洁：新增文件、代码、依赖和抽象是否必要；是否存在重复系统。
4. 缺陷与稳定：崩溃、软锁、卡死、错误状态、资源泄漏。
5. 性能：帧时间、内存、加载时间、发热/耗电（目标设备支持时）。
6. 可维护：代码定位难度、模块边界、配置可理解性、修改成本。
7. 兼容性：锁定引擎版本、目标平台和设备是否一致通过。
8. 可复现性：输入、版本、种子、环境和证据是否完整。

不将八项简单平均掩盖关键失败。核心玩法错误、存档丢失、严重崩溃、触控无法操作属于一票否决。

## 复杂度成本

记录每组：
- 新增/修改文件数；
- 新增代码行数（仅作诊断，不以越少越好）；
- 新增依赖与安装体积；
- 新增服务、线程、定时器和后台任务；
- 实现耗时、排错耗时、回归耗时；
- 新增缺陷、修复缺陷、回归失败数量。

如果技能提高文档完整度，却增加无需求框架、引擎无关抽象或大量依赖，应降低评价。

## 证据等级

- E0 未执行：只有文档或上游说明。
- E1 静态审阅：检查正文、引用、脚本和许可证。
- E2 工具测试：脚本、单元测试或静态检查实际运行。
- E3 引擎集成：目标引擎真实构建、运行、自动化场景通过。
- E4 真实设备/玩家：目标设备操作、性能采样和人工试玩通过。

技能等级：
- A：在至少一个明确适用的真实项目达到 E3；关键体验类技能还需 E4。
- B：已导入并完成基本静态审阅，尚未在目标项目验证。
- C：候选来源，许可证/适用范围/依赖尚未审完。
- D：不适用、过时、不可复现、严重误导或不符合许可要求。

## 验收报告模板

每轮报告必须包括：
- 任务 ID、游戏项目、引擎/版本、平台、代码提交、资产版本；
- A/B/C 组使用的技能和精确版本；
- 复现步骤、配置、随机种子、驱动方式；
- 静态检查、自动化测试、引擎集成、真实设备/玩家结果；
- 八项评分、复杂度成本和缺陷明细；
- 原始截图/日志/录屏/性能采样的证据位置；
- 结论：保留、精简、合并、条件启用或淘汰；
- 未验证项和下一次验证条件。

**禁止行为：** 没有实际执行就写“测试通过”；把模型自评当作玩家测试；把静态代码检查当作可玩验收；为提高分数隐藏新增复杂度或失败样本。

## 当前状态

本规范已写入仓库，尚未对用户某个具体游戏项目执行 A/B 对照实验。所有已导入第三方技能仍按 B 级或待审级管理，不得虚报为 A 级。

## AI 编写游戏代码专项基准

本节用于评估通用 AI 编程工程技能是否真的改善游戏代码，不用上游宣传或模型自评代替实测。

| 编号 | 固定任务 | 必须观察的结果 |
|---|---|---|
| CODE-BENCH-01 | 按明确验收条件增加一个小型玩法功能 | 需求覆盖、最小实现、边界状态、可回归测试 |
| CODE-BENCH-02 | 修复一个有稳定复现步骤的 Bug | 先复现、定位根因、旧代码测试失败、修复后通过 |
| CODE-BENCH-03 | 重构一个存在重复逻辑的模块 | 对外行为不变、历史行为回归、复杂度没有无故上升 |
| CODE-BENCH-04 | 设计一个跨模块游戏系统 | 模块职责、依赖方向、状态流、数据契约、非目标与迁移路径 |
| CODE-BENCH-05 | 处理一项掉帧/内存增长问题 | 先有同设备基线和性能采样，再做针对性优化与复测 |
| CODE-BENCH-06 | 修改存档字段或内容 ID | 旧样本迁移、失败保护、备份恢复、原始数据不被覆盖 |
| CODE-BENCH-07 | 引入一个第三方游戏插件/库 | 许可证、引擎兼容、来源、依赖、包体和最小集成验证 |

### 对照组与记录要求

- A 组：只使用仓库原有 AGENTS.md 与基础工作流，不加载新增通用工程技能。
- B 组：加载 AI 游戏代码工程总规范，并按路由使用对应的 1–3 项专业技能。
- C 组（可选）：使用精简组合，判断多技能叠加是否带来真实收益。
- 各组使用相同需求、相同代码提交基线、相同引擎版本、相同工具权限、相同验收用例和相同设备。
- 每个任务每组至少重复 3 次；记录模型、运行设置、输入、代码提交、测试命令、完整结果和时间。
- 不允许 A 组故意不读项目约定，也不允许 B 组获得额外未记录的需求信息。
- 如果无法复用同一工程基线，结果标记为不可比较，不做技能优劣结论。

### 代码工程评分（每项 0–5）

1. 需求正确性：验收条件逐条实现，没有私自改变行为。
2. 根因与缺陷控制：修复命中根因，缺陷有可复现回归测试。
3. 历史兼容：未破坏既有输入、存档、内容 ID、关卡、平台和 API 行为。
4. 架构与职责：模块边界清楚，依赖方向合理，没有无意义的框架化。
5. 可维护性：命名、类型、错误处理、注释、代码重复和死代码符合项目约定。
6. 测试质量：测试能在错误实现上失败，覆盖关键边界与状态转换。
7. 运行质量：真实构建、运行、设备输入和性能结果符合目标平台要求。
8. 证据可信度：版本、命令、输出、日志和截图可复核，未验证项明确。

核心功能错误、玩家数据丢失、无法启动、关键崩溃或作弊/权限边界失效均为一票否决。不得用其他维度高分抵消。

### 复杂度与成本单独记录

记录新增/修改文件、代码量、依赖、服务、线程、状态机、配置项、维护步骤、实现时间、排错时间、回归时间及新增缺陷。代码行数仅用于解释变化，不以越少越好。技能若提升正确性但明显增加无必要复杂度，必须考虑精简或改为条件启用。
