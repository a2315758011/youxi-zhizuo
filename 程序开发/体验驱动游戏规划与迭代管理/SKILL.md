# 体验驱动的游戏规划与迭代管理

## 适用范围

用于从零立项、重整长期游戏计划、功能堆积失控、各模块成熟度失衡、迭代结束却没有可试玩成果等情况。

它是规划方法，不替代项目执行台账、资源锁、代码测试或真实试玩。小型单功能修复不必套用完整层级。

## 核心原则

1. 从玩家最终能体验到什么开始，而不是先堆功能清单。
2. 优先验证风险最高、验证成本最低的假设。
3. 每个迭代都必须产出可试玩或可检查的成果。
4. 保持玩法、技术、美术、关卡、输入和发布能力的整体平衡，避免某一模块过度精修而其他关键模块仍未知。
5. 失败时回到最近一个有效成果，不从头重做。
6. 复杂度必须有收益依据；不为可视化而增加长期服务、数据库或大型依赖。

## 规划流程

### 1. 定义玩家体验

写清楚：
- 玩家是谁、在什么设备和场景下玩。
- 玩家反复执行的核心动作。
- 一局游戏从开始到结束的体验变化。
- 最重要的乐趣、压力、策略或情绪回报。
- 成功体验成立所依赖的关键假设。
- 最便宜的验证方法和失败回退条件。

### 2. 划分核心支柱

只保留不能合理归入其他支柱的高层能力，例如：
- 核心玩法与战斗循环
- 关卡与成长
- 经济与资源
- 美术、动画与反馈
- 输入、UI 与可访问性
- 技术、性能与跨平台交付

简单项目可以合并支柱，避免为了表格而拆分。

### 3. 拆分玩家功能与支撑能力

- 玩家功能：玩家能直接感知的玩法和体验。
- 支撑能力：为多个玩家功能提供支持的技术或生产能力，例如存档、资源加载、构建、性能和测试。

每项功能至少记录：稳定 ID、所属支柱、依赖、当前证据级别、目标证据级别、负责人、状态、当前迭代和证据链接。

### 4. 使用四级证据成熟度

| 等级 | 含义 | 最低证据 |
|---|---|---|
| L1 概念 | 文字、草图、规则假设 | 明确假设与风险 |
| L2 原型 | 白盒、临时素材、可操作原型 | 能验证核心规则或体验 |
| L3 实现 | 稳定代码、正式资源和 UI | 目标用户可完成主要流程 |
| L4 打磨 | 性能、手感、平衡、边界修复 | 目标设备回归和发布证据 |

等级描述的是**单项功能的证据成熟度**，不是整个项目完成百分比。项目总进度仍按仓库既定的里程碑、权重和验收证据计算，不能把 L1-L4 简单平均冒充总进度。

不要在相邻核心功能仍停留在 L1 时，把单个功能提前打磨到 L4；特殊演示版本可以例外，但必须标明它是倾斜迭代。

### 5. 拆成可执行任务

只有到了任务层才分配直接执行工作。任务应具备：
- 明确输入和输出；
- 单一主要负责人；
- 可复现的完成条件；
- 所属功能和迭代；
- 状态、阻塞原因和验收证据。

如果任务仍需要大量概念设计，应退回功能或概念层重新拆解。

### 6. 设计迭代

每轮迭代写明：
- 目标玩家体验；
- 本轮覆盖的核心支柱；
- 哪些功能要提升证据等级；
- 最小任务集合；
- 可试玩/可检查成果；
- 验收方式；
- 回滚条件。

优先让每轮迭代都保留一条完整、粗糙但可玩的主循环，而不是只交付孤立模块。

## 评审清单

- 是否从玩家体验出发，而不是功能堆积？
- 关键假设是否显式列出并按风险排序？
- 验证方式是否足够便宜？
- 支柱和功能是否清晰，是否过度拆分？
- 每项功能是否有当前等级、目标等级和证据链接？
- 是否区分玩家功能与支撑能力？
- 是否存在一个模块过度打磨、其他关键模块仍未知？
- 每轮是否产出可试玩或可检查的成果？
- 是否记录阻塞、负责人和回滚点？

## 使用限制

- 不替代 Project Orchestrator 任务台账、工程规则门禁、资源锁和自动化测试。
- 不用热力图、成熟度平均值或任务数量制造虚假的完成百分比。
- 不默认安装或引入上游可视化脚本；只有用户明确需要可视化时，才单独评估工具和依赖。
- 对多人联网、支付、账号、云存档等复杂能力，只有游戏确实需要时才增加相应架构。
